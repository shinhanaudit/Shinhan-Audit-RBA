# 감사 체크리스트 생성

금융감독원(금감원, FSS) 자료를 바탕으로 특정 업권의 감사 체크리스트를 만드는 워크플로우다.
크롤링과 텍스트 추출은 결정적 작업이라 스크립트로 처리하고, 리스크 식별과 표 작성은 판단이 필요하므로 직접 읽고 작성한다.

## Phase 0: 컨텍스트 확인

작업 전 `data/{업권}/` 폴더가 이미 있는지 확인한다.

- 폴더가 없다 → **초기 실행** (Phase 1부터)
- 폴더가 있고 사용자가 새 기간/새 크롤링을 요청 → **재실행** (Phase 1부터, 기존 파일은 자동으로 스킵되므로 안전하게 재사용 가능)
- 폴더가 있고 사용자가 "이 항목 빼줘/보강해줘/이 리스크 더 자세히" 같은 표 수정만 요청 → Phase 4로 바로 이동, 크롤링·추출 재실행 없이 기존 데이터로 표만 수정

## Phase 1: 기관명·업권·감사기간 확인

사용자 메시지("26년 3월 신한은행 감사업무 시작" 등)에서 기관명과 업권을 파악한다. `config/industries.py`의 `INDUSTRY_CODES`, `INDUSTRY_KEYWORDS`를 참고한다.

**업권 판단 우선순위**:
1. **먼저 `config/industries.py`의 `COMPANY_INDUSTRY_MAP`에서 기관명을 찾는다.** 신한 계열사(신한은행/신한카드/신한투자증권/신한라이프/신한캐피탈/신한자산운용/제주은행/신한저축은행/신한자산신탁/신한DS/신한펀드파트너스/신한리츠운용/신한벤처투자/신한EZ손해보험 등)는 내부적으로 "자본시장업권", "여신전문금융업권"처럼 부르지만 이 라벨은 금감원 검사업무안내서 게시판(selectCate)에 존재하지 않는 명칭이다. 크롤링에는 반드시 `COMPANY_INDUSTRY_MAP`이 매핑해둔 **실제 금감원 업권 키 목록**(`INDUSTRY_CODES`의 키, 리스트 형태)을 사용한다 — 예: 신한투자증권(내부 라벨 "자본시장업권") → 실제로는 `증권선물`, 신한자산운용·신한자산신탁(내부 라벨 "자본시장업권") → 실제로는 `증권선물`+`자산운용` 2개 업권 모두, 신한카드/신한캐피탈/신한저축은행/신한벤처투자(내부 라벨 "여신전문금융업권" 등) → 실제로는 `비은행`. **매핑 값이 2개 이상이면 Phase 2에서 각 업권을 모두 크롤링해 같은 회사 폴더에 병합한다.**
2. **`COMPANY_INDUSTRY_MAP`에 없는 기관명**이면 아래 일반 판단 기준으로 추정하고, 사용자에게 확인받을 때 "내부 업권 라벨"이 아니라 이 실제 매핑 결과를 제시한다:
   - 은행(시중은행, 지방은행) → `은행`
   - 저축은행/대부업/여신전문 → `비은행`
   - 생명/손해보험사 → `보험`
   - 증권사/투자매매업 → `증권선물`
   - 자산운용사/투자신탁 → `자산운용`
   - 지주회사/복합금융/신탁 → `복합금융`
   - 신용정보사/카드사 → `신용감독`
   - 회계법인/감사인 → `기업회계감사`
   - 퇴직연금/자금세탁방지/IT·금융인프라 등 딱 맞는 업권이 없는 공통 이슈 → `공통`
3. **`COMPANY_INDUSTRY_MAP`에 정기감사 대상 여부가 불확실하다고 주석 처리된 기관(신한DS, 신한벤처투자 등)**은 크롤링 전 사용자에게 "이 기관이 금감원 정기감사 대상이 맞는지, 맞다면 `공통`/`비은행` 카테고리로 크롤링해도 되는지"를 반드시 재확인한다 — 이 두 곳은 금감원 9개 업권(은행/비은행/보험/증권선물/자산운용/복합금융/신용감독/기업공시/기업회계감사) 중 어디에도 명확히 속하지 않아 임의 배정한 값이기 때문이다.

**업권을 확정하기 전에, 그리고 크롤링을 시작하기 전에 반드시 아래 두 가지를 사용자에게 되물어 확인한다** (한 번에 같이 물어도 된다):

1. **기관명(회사명)**: 사용자 메시지에 이미 명시돼 있으면("신한은행") 그대로 확인만 받는다. 업권 전체(회사 특정 없이 "저축은행 감사")를 원하는 요청이면 기관명 없이 업권 전체로 진행할지 확인한다.
2. **감사 기간**: 감사 시작일~종료일을 명시적으로 받는다 ("2026-03-01 ~ 2026-03-31"처럼 구체적 시작일/종료일). 사용자가 "26년 3월"처럼 월 단위로만 말하면 해당 월의 1일~말일을 감사 기간으로 확정해도 되는지 확인한다. **기본값(최근 3개월 window, 최근 12개월)을 임의로 적용하지 않는다** — 감사 기간은 항상 사용자가 확정한 값을 그대로 쓴다.

확인 예시: "'신한투자증권'(내부 라벨: 자본시장업권 → 금감원 실제 업권: 증권선물), 감사 기간 2026-03-01~2026-03-31로 크롤링할까요?" 업권이 2개 이상 매핑된 경우 예시: "'신한자산운용'(내부 라벨: 자본시장업권 → 금감원 실제 업권: 증권선물 + 자산운용, 두 업권 모두 크롤링), 감사 기간 ...로 크롤링할까요?" 내부 라벨과 실제 크롤링 업권이 다른 경우 반드시 둘 다 보여준다. 이 프로젝트를 감사팀이 실무에 쓰므로, 엉뚱한 업권·기간으로 크롤링해 자료를 낭비하면 안 된다.

## Phase 2: 크롤링

`crawler/fss_crawler.py`를 도구로 직접 실행한다. Phase 1에서 확정한 감사 기간을 `--start`/`--end`(YYYY-MM-DD)로 그대로 넘긴다 — 이 값이 있으면 크롤러는 근사 window 없이 해당 구간만 정확히 수집한다. 기관명이 있으면 `--company`로 넘겨 검사결과제재·경영유의사항을 그 기관으로만 필터링한다(업권 전체가 아니라 감사대상 기관 자체 자료 위주로 모으기 위함).

```bash
python -m crawler.fss_crawler <업권명> --out data --start <YYYY-MM-DD> --end <YYYY-MM-DD> --company <기관명, 선택> --manual-pages 3 --sanction-pages 5 --impr-pages 5
```

`COMPANY_INDUSTRY_MAP`에서 업권 키가 2개 이상 매핑된 회사(예: 신한자산운용 → 증권선물+자산운용)는 위 명령을 업권마다 한 번씩 반복 실행한다. `--out data`는 동일하게 유지하면 크롤러가 `data/<업권명>/` 아래 각각 저장하므로 폴더가 겹치지 않는다 — Phase 4에서 두 업권 폴더를 모두 순회해 근거를 취합한다.

- `<업권명>`은 `config/industries.py`의 키(은행/비은행/보험/증권선물/자산운용/복합금융/신용감독/기업공시/기업회계감사/공통) 중 하나를 그대로 쓴다.
- `--start`/`--end`를 생략하면(사용자가 기간을 특정하지 않겠다고 명시한 예외적 경우에만) 크롤러가 "오늘 기준 최근 12개월"로 안전하게 제한한다 — 하지만 Phase 1에서 항상 기간을 확정받으므로 정상 흐름에서는 이 기본값을 쓸 일이 없어야 한다.
- 검사업무안내서(1순위 자료)는 업권 단위 문서라 `--company` 필터가 적용되지 않는다 — 업권 코드로만 걸러진다. 제재·경영유의사항은 `--company`가 있으면 업권 키워드 대신 기관명으로만 매칭한다.
- 실행 후 stdout에 카테고리별 저장 건수가 출력된다. 0건인 카테고리가 있어도 정상일 수 있다(해당 기간에 실제로 게시물이 없을 수 있음) — 에러가 아니라면 계속 진행한다.
- **저장소 루트에 `.venv` 폴더가 있으면(`install.ps1`/`install.bat`로 설치한 정상 환경) 항상 `.venv\Scripts\python.exe`(Windows) 또는 `.venv/bin/python`(macOS/Linux)를 명시적으로 사용한다.** `.venv`가 없거나 Python 인터프리터 경로가 여러 개인 환경이면 `pip install -r requirements.txt`가 된 인터프리터를 찾아 명시적으로 지정한다.

## Phase 3: 텍스트 추출

다운로드된 hwp/pdf 원문을 텍스트로 변환한다. 이 단계 없이는 근거(페이지/조항)를 지어내게 되므로 반드시 실행한다.

```bash
python .claude/skills/fss-audit-checklist/scripts/extract_text.py data/<업권명>
```

- pdf는 `pdfplumber`, hwp는 `hwp5txt`(pyhwp 패키지)로 추출한다. 둘 다 설치되어 있어야 한다:
  `pip install pdfplumber pyhwp`
- 이미 추출된 파일(`*.extracted.txt` 존재)은 자동 스킵되므로 재실행해도 안전하다.
- hwp5txt가 설치되지 않은 환경이면 hwp 파일은 건너뛰고 경고만 출력한다 — 이 경우 검사업무안내서 근거가 부실해질 수 있음을 사용자에게 알린다.
- 검사업무안내서가 `.zip`(여러 hwp 챕터 묶음, 증권선물/자산운용 등에서 흔함)으로 배포된 경우 `extract_text.py`가 폴더 스캔 시 자동으로 `{zip이름}_unzipped/`에 풀어서 처리한다. 스크립트 출력에 `[압축해제]` 로그가 없는데 검사업무안내서 카테고리 원본이 `.zip`이면 압축이 안 풀린 것이니 폴더를 직접 확인한다.
- **일부 hwp 파일은 pyhwp 라이브러리 자체의 파싱 한계(OLE 속성 스트림의 특정 타입을 지원하지 않아 `KeyError` 등으로 실패)로 추출이 안 될 수 있다.** 이는 우리 스크립트나 설치 문제가 아니라 pyhwp의 알려진 제약이므로, `[실패]` 로그가 뜬 파일을 재설치·재시도로 해결하려 하지 말고 해당 파일만 근거 부족으로 처리한다 — hwp5txt 미설치 시와 동일하게 그 카테고리는 제재/경영유의사항 위주로 보강하고 사용자에게 몇 건이 추출 실패했는지 알린다.

## Phase 4: 체크리스트 작성

`data/<업권명>/` 아래 세 카테고리 폴더(검사업무안내서/검사결과제재/경영유의사항)를 순회하며 다음을 읽는다:
- `*.txt` (메타데이터: 제목/부서/등록일/원문 링크)
- `*.extracted.txt` (실제 본문 — 있으면 반드시 이것을 근거로 삼는다)

**우선순위(2단계)**: 1순위는 검사업무안내서 본문이다 — 여기서 뽑을 수 있는 리스크를 먼저 채운다. 2순위는 검사결과제재와 경영유의사항인데, 이 둘은 서로 우열이 없는 동급이다(제재=경영유의사항) — 1순위로 다 채우지 못한 부분을 이 둘로 보강한다. 검사업무안내서는 목차에 페이지 번호가 포함되어 있으므로(`extract_text.py` 출력에서 확인 가능), 근거 컬럼에 실제 페이지 번호를 적을 수 있으면 적는다.

**근거를 지어내지 않는다.** `.extracted.txt`에 없는 내용을 근거로 인용하지 말 것 — 확인 안 되면 "검사업무안내서 자금세탁방지 검사사항" 처럼 문서명+주제까지만 쓰고 페이지는 생략한다.

**대용량/다건 처리 (통짜로 읽지 않는다)**: 아래 조건 중 하나라도 해당하면 전체 파일을 순서대로 Read하는 대신 반드시 아래 절차를 따른다.
- 카테고리 폴더 내 `.extracted.txt` 파일 수가 10개를 초과
- 개별 `.extracted.txt`가 500줄(또는 약 20KB) 초과

절차:
1. **먼저 목차만 스캔한다.** Grep으로 각 파일의 항목 헤더 패턴(예: `^\(\d+\) .+$`, `제\d+장`, `\d{3}\. ` 등 검사업무안내서/경영유의사항 특유의 번호매김)을 카테고리 전체에 대해 한 번에 돌려 소제목 목록을 먼저 확보한다. 이 결과만으로 테마 분류와 표 뼈대를 잡는다.
2. **인용이 필요한 항목만 부분 Read한다.** 근거로 쓸 항목이 정해지면 Grep의 라인 번호를 기준으로 Read에 `offset`/`limit`을 지정해 해당 항목 주변만 읽는다. 파일 전체를 여는 것은 소수의 짧은 파일(500줄 이하)에만 허용한다.
3. **파일 묶음이 많으면 서브에이전트에 위임한다.** 한 카테고리의 파일 수가 많아(대략 8개 이상) 순차 Grep/Read로도 컨텍스트 소비가 클 것으로 예상되면, 파일을 몇 묶음으로 나눠 `Agent`(subagent_type: `general-purpose`, 여러 묶음이면 병렬 호출)에 위임한다. 프롬프트에는 반드시 다음을 명시한다:
   - 대상 파일 경로 목록(묶음별)
   - "리스크 후보만 추출하라: 테마 / 소제목 / 리스크 1문장 / 감사항목 후보 / 근거(파일명 + 항목번호 또는 페이지) 형식으로, 원문에 없는 내용은 근거로 쓰지 말 것"
   - 출력은 표 형태 텍스트로, 항목당 한 줄
   - 서브에이전트 결과는 그대로 신뢰하지 말고, 표에 반영하기 전 근거 문구가 실제 원문과 맞는지 최소 표본 확인한다(전체 재검증은 불필요).
4. 메인 세션은 이렇게 모인 후보 목록을 취합해 Phase 4 표 형식으로 정리·중복제거·리스크ID 부여만 수행한다 — 원문 재열람은 근거를 구체화할 때만 최소한으로 한다.

**결과물은 채팅창에 markdown 표로 찍지 않고, 실제 표 파일(CSV)로 만든다.** 감사팀이 엑셀 등에서 그대로 열어보는 용도이기 때문이다.

- 컬럼 체계는 `리스크ID|테마|소제목|리스크|감사항목|근거` 6개다 (스킬 description·CLAUDE.md에 명시된 것과 동일). CSV 헤더 행도 정확히 이 6개 이름을 그대로 쓴다: `리스크ID,테마,소제목,리스크,감사항목,근거`. 공백 삽입(`리스크 ID`)이나 괄호 설명(`리스크(1문장)`, `감사항목(설계/운영)`) 추가, 컬럼 추가/삭제를 하지 않는다.
- **저장 경로**: `data/<업권명>/checklist_<날짜 YYYYMMDD>.csv`.
- **CSV를 절대 Write 도구로 직접 조립하지 않는다.** 셀 값에 쉼표·줄바꿈·따옴표가 섞이면 수동으로 "필드,필드,필드" 문자열을 이어붙이는 순간 이스케이프가 깨지고, 엑셀에서 컬럼이 밀린다(실제로 한 번 발생했던 문제). 대신 항상 다음 2단계를 거친다:
  1. 행 데이터를 JSON 배열로 만들어 임시 파일에 Write한다. 각 원소는 `{"리스크ID": ..., "테마": ..., "소제목": ..., "리스크": ..., "감사항목": ..., "근거": ...}` 형식이다(JSON은 문자열 이스케이프가 표준 문법이라 쉼표·줄바꿈이 섞여도 깨지지 않는다).
  2. `python .claude/skills/fss-audit-checklist/scripts/write_checklist_csv.py <임시.json> data/<업권명>/checklist_<날짜>.csv`를 실행해 CSV로 변환한다. 이 스크립트가 `csv` 모듈로 이스케이프·BOM(UTF-8-sig, 엑셀 한글 깨짐 방지)을 전담한다.
  3. 스크립트가 `[실패]`를 출력하면(컬럼 누락 등) 임시 JSON을 고쳐서 재실행한다 — CSV 파일을 손으로 고치지 않는다.
- 리스크 ID는 `R{순번}-{일련번호}` 형식으로 항목마다 고유하게 부여한다 (테마별로 묶어 순서대로).
- "리스크" 컬럼은 한 문장으로 끝낸다. 여러 문장을 이어붙이지 않는다 — 부연이 필요하면 근거 컬럼이나 감사항목 컬럼에 녹인다.
- **감사대상 기관 자체 자료가 아니라 동일 업권 타사·인접업권 사례를 근거로 쓴 행은 근거 컬럼 맨 앞에 `[타사]` 태그를 붙인다** (예: `[타사] 제재내용공개안(KB증권, 2026.6.17.) 문책사항(2)`). 감사대상 기관 자체 근거는 태그 없이 그대로 쓴다.
- **파일을 쓰기 전 마지막에 헤더 행이 위 6개 컬럼명과 정확히 일치하는지 스스로 대조한다.**
- 목표 항목 수는 약 40개. 검사업무안내서에서 뽑을 수 있는 항목이 적으면 억지로 채우지 말고, 실제 원문에서 확인되는 만큼만 제시하고 사용자에게 "원문 근거가 부족해 40개에 못 미친다"고 알린다.
- **채팅 응답 형식**: CSV 파일을 쓴 뒤, 채팅에는 (1) 원문 근거가 부족한 경우 그 사실 한두 문장, (2) 저장된 파일 경로와 총 항목 수, (3) 테마별 항목 수 요약(짧은 목록, markdown 표 아님), (4) "추가로 보강하거나 제거할 항목이 있으면 말씀해주세요." 한 줄만 출력한다. 표 내용 전체를 채팅에 다시 markdown 표로 옮겨 적지 않는다 — 사용자가 요청하면 그때 파일 내용 일부를 보여준다.

## Phase 5: 컨펌 루프

사용자 피드백("이 항목 빼줘", "~ 관련 리스크 추가해줘", "근거 더 구체적으로")을 받으면:
- 채팅에 표 전체를 다시 옮겨 적지 않는다. **CSV 파일을 Edit나 Write로 직접 고치지 않는다** — Phase 4와 동일하게, 기존 CSV를 읽어(Read 또는 csv 모듈) 행 데이터를 얻은 뒤 필요한 행만 추가/수정/삭제한 JSON을 만들고, `write_checklist_csv.py`를 다시 실행해 전체 CSV를 재생성한다. 사람이 CSV 텍스트를 직접 편집하면 이스케이프가 깨질 수 있기 때문이다. 채팅에는 변경 요약만 prose 목록으로 안내한다:
  - `[신규] R#-###: 소제목` — 이번 턴에 새로 추가된 항목
  - `[수정] R#-###: 소제목 (무엇이 바뀌었는지 한 구절)` — 기존 항목의 리스크/감사항목/근거 등이 변경된 항목
  - `[삭제] R#-###: 소제목 (사유)` — 제거 요청된 항목은 CSV에서 행을 빼고 요약에 남긴다
  - 언급되지 않은 기존 행은 이번 턴에 변경되지 않았다는 뜻이다.
- 리스크 ID는 기존 항목 번호를 유지하고, 신규 항목만 다음 번호를 이어서 부여한다 (사용자가 특정 항목을 참조하기 쉽게).
- CSV를 고칠 때도 Phase 4의 헤더·컬럼 규칙(정확히 `리스크ID,테마,소제목,리스크,감사항목,근거`, `[타사]` 태그 규칙 등)을 그대로 지킨다.
- **피드백이 "카테고리로 돌아가서 더 반영해줘"류(예: "경영유의사항 쪽 더 반영해줘", "제재 사례도 훑어줘")로 구체적 항목·조문을 특정하지 않은 경우:**
  - 기억이나 대화 앞부분에서 이미 읽은 내용에 의존해 근거를 만들어내지 않는다. Phase 4의 "대용량/다건 처리" 절차(먼저 Grep으로 해당 카테고리 전체의 헤더/소제목 목록을 다시 스캔 → 이미 CSV에 반영된 항목과 대조해 아직 안 다룬 후보만 추림)를 그대로 다시 수행한다.
  - 스캔 결과 후보가 여러 개면 전부 임의로 채우지 말고 후보 소제목 목록을 사용자에게 먼저 보여주고 어떤 걸 반영할지 확인한다. 사용자가 "다 반영해줘"라고 명시하면 그때만 전체를 반영한다.
  - 사용자가 항목 번호나 소제목을 특정해서 말하면(예: "(30)번도 반영해줘") 위 스캔 없이 바로 Grep으로 해당 항목의 시작 라인을 찾아 offset/limit으로 부분 Read해 근거를 확보한다.
- 사용자가 "더 고칠 것 없다/됐다/완료" 등으로 만족을 표시하면, 곧바로 종료하지 말고 다음을 확인한다:
  1. 최종 CSV 파일 경로를 알려주며 확정을 안내한다(파일은 Phase 4부터 이미 `data/<업권명>/checklist_<날짜>.csv`에 저장되어 있으므로, 이 시점엔 별도 저장 여부를 묻지 않고 최종 경로만 재확인한다).
  2. 이어서 **`fss-audit-checklist-news` 스킬 실행 여부를 제안**한다 (예: "최근 언론 보도 기준으로 이 업권/기관 관련 이슈가 있는지 확인해서 체크리스트에 반영할까요?"). 사용자가 원하면 해당 업권명과 (있다면) 기관명을 인자로 넘겨 `fss-audit-checklist-news`를 호출한다. 원치 않으면 다음 단계로.
  3. 체크리스트가 최종 확정된 시점(뉴스 반영까지 마쳤거나, 사용자가 뉴스 반영을 건너뛰기로 한 시점)에 **Gmail 초안 발송 여부를 제안**한다 (예: "확정된 체크리스트를 메일로 보내드릴까요?"). 사용자가 원하면:
     - 수신자 이메일 주소를 아직 모르면 반드시 먼저 물어본다(추측·생략 금지).
     - **CSV 파일을 첨부하지 않는다** — 받는 사람이 파일을 못 여는 환경일 수 있으므로, 표를 메일을 열자마자 바로 보이고 그대로 복사해 엑셀 등에 붙여넣을 수 있는 형태로 본문에 직접 넣는다.
     - `mcp__claude_ai_Gmail__create_draft` 호출 시 `htmlBody`와 `body`를 함께 채운다:
       - `htmlBody`: CSV를 읽어 `<table><thead><tr><th>리스크ID</th>...</tr></thead><tbody>...`로 실제 HTML 표를 만든다. 각 셀은 `<td>`, 헤더는 6개 컬럼(`리스크ID/테마/소제목/리스크/감사항목/근거`) 그대로 유지한다. 이렇게 만들면 받는 사람이 표를 그대로 드래그해 엑셀에 붙여넣어도 열이 유지된다. 셀 값에 `<`, `>`, `&`가 있으면 HTML 이스케이프한다.
       - `body`(plain-text 대체용): 마크다운 표 문법(`| 리스크ID | 테마 | ... |` 헤더 구분선 포함)으로 동일한 내용을 적는다. HTML을 못 보는 메일 클라이언트에서도 사용자가 그대로 복사해 마크다운을 지원하는 곳(노션 등)에 붙여넣을 수 있게 하기 위함이다.
     - 제목은 `[감사팀] <업권/기관명> 감사 체크리스트 (checklist_<날짜>, 총 N건)` 형식으로 짓는다.
     - Gmail MCP 도구는 초안(draft) 생성까지만 가능하고 실제 발송은 지원하지 않는다 — 초안을 만든 뒤에는 "Gmail에서 확인 후 직접 보내야 한다"고 사용자에게 안내한다. 실제 발송을 자동화한 것처럼 말하지 않는다.
     - 사용자가 원치 않으면 이 단계를 건너뛰고 종료한다.

## 참고: 웹 UI (선택)

`app/` 아래 FastAPI 기반 로컬 웹 채팅 UI도 동일한 크롤러를 사용해 같은 작업을 할 수 있다 (`python -m uvicorn app.main:app --port 8811`). 다만 hwp/pdf 텍스트 추출과 근거 있는 표 작성은 이 스킬(Claude Code 세션)에서 수행하는 편이 근거 품질이 높다 — 웹 UI의 LLM 연동(`app/llm.py`)은 아직 이 텍스트 추출 단계를 반영하지 않았으므로, 정확한 결과가 필요하면 이 스킬을 통해 진행할 것을 권장한다.
